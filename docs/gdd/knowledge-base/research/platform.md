# Платформа — веб (ManyPlay), ограничения и решения

Фрейм (00_MASTER): только web, Canvas 2D поле + UI Kit поверх, онлайн-игра платформы (`online: true`), все сервисы через ManyPlay SDK 1.0.0-rc.30. **Рекламы нет вообще**, монетизация — только IAP через SDK.

## 1. Три ориентации, все равноправны (`orientation_fixed = false`)

Поле — квадрат 13×13 клеток, `cellPx = floor(fieldPx / 13)` (00_MASTER §5). Ниже прикидки размеров. Это **оценка**, точные отступы и HUD задаёт раздел 20.

| Профиль | Вьюпорт | Раскладка | Поле (оценка) | Клетка (оценка) |
|---|---|---|---|---|
| portrait | 390×844 | поле сверху на всю ширину; HUD над полем; стик и FIRE/бустеры снизу | ~390 px (без боковых полей) | 30 px |
| landscape | 844×390 | поле по центру по высоте; слева стик и инфо, справа FIRE и бустеры | ~364 px (390 минус safe area/HUD) | 28 px |
| desktop | 1440×900 | поле по центру; HUD и счётчики по бокам; управление клавиатурой | ~780–840 px | 60–64 px |

Следствия:
- Landscape 844×390 — самый тесный профиль. Клетка 28 px — минимум, при котором танк читается (оценка). HUD не кладём поверх поля, только по бокам.
- В портрете палец не должен закрывать поле: все тач-контролы ниже поля.
- При смене ориентации посреди стадии нужны пауза и пересчёт раскладки без потери состояния (оценка; критерий для QA, раздел 40).
- Safe area (вырезы, жестовая полоса) учитываем через `env(safe-area-inset-*)` (практика веба, оценка).

## 2. Вес первой загрузки

| Ориентир | Значение | Источник |
|---|---|---|
| Poki (цель) | начальная загрузка ≤ 5 МБ, всего ≤ 8 МБ; уходят, если грузится > 10 с | [paweljarosz.pl](https://www.paweljarosz.pl/blog/html5-game-optimization.html), [bountyboard.gg](https://www.bountyboard.gg/blog/how-to-submit-an-html5-game-to-web-platforms) |
| CrazyGames | начальная ≤ 50 МБ; для мобильной витрины ≤ 20 МБ | [CrazyGames docs](https://docs.crazygames.com/requirements/technical/) |
| Facebook Instant Games | старт < 5 с, лучше < 3 с | [paweljarosz.pl](https://www.paweljarosz.pl/blog/web-porting.html) |

**Наша цель (оценка):** до первого кадра Lobby ≤ 3 МБ, до старта стадии 1 ≤ 5 МБ. Музыку глав 2–3, арт глав 2–3 и Siege догружаем в фоне. Canvas 2D и тайловая графика 13×13 позволяют уложиться: атласы спрайтов, WebP, аудио в сжатом формате, один музыкальный трек на старте. Боремся и с числом файлов: CrazyGames ограничивает их количество, потому что много файлов замедляет загрузку ([CrazyGames docs](https://docs.crazygames.com/requirements/technical/)).

## 3. Тач-управление: стик + FIRE

Решение 00_MASTER: виртуальный стик слева/снизу, кнопка FIRE справа/снизу, кнопки бустеров. Практики:
- **Плавающий стик в зоне активации** (центр там, куда лёг палец, в левой половине нижней зоны). Это лучший дефолт для экшена: фиксированный стик «наказывает» за неточное касание ([simplified.media](https://simplified.media/guides/mobile-touch-controls), [getflikk](https://getflikk.com/blog/mobile-game-controls)).
- **Радиус хода** ≈ 15–20 % короткой стороны, то есть ~60–80 CSS px на ширине 390 ([simplified.media](https://simplified.media/guides/mobile-touch-controls)).
- **Таргеты** ≥ 44×44 CSS px; у FIRE и бустеров зона касания шире нарисованной кнопки ([simplified.media](https://simplified.media/guides/mobile-touch-controls)).
- **Мультитач.** Вызывать `setPointerCapture()` на pointerdown, иначе стик «замерзает», когда палец съезжает за пределы элемента ([simplified.media](https://simplified.media/guides/mobile-touch-controls)).
- **4 направления.** Танк ездит по 4 осям, поэтому вектор стика квантуется в доминирующую ось с гистерезисом, чтобы на диагонали направление не дребезжало (оценка, детали в разделе 10). Нужна мёртвая зона.
- **Удержание FIRE = автоогонь** с темпом пушки, чтобы не долбить кнопку (оценка; решение раздела 10).
- Настройка «стик слева/справа» — по желанию, в Settings ([simplified.media](https://simplified.media/guides/mobile-touch-controls)). В MVP можно не делать.
- Веб-специфика: `touch-action: none` на поле, запрет pinch-zoom и pull-to-refresh, разблокировка аудио первым жестом, пауза по `visibilitychange` (практика веба, оценка).

## 4. Покупки — только через SDK ManyPlay

- Модуль `iap` (`iapModule({})` из `@manygamescorp/mod-iap/iap`, функции `offers`, `purchase`; docs/sdk/modules.md).
- Паки и их содержимое (бустеры из `inventory`) игра читает из configs (`iap.*`), SKU в коде не хардкодятся (00_MASTER §6, §11).
- Пока владелец не подключил оплату, покупки тестовые (00_MASTER §12). UI честно показывает результат покупки (S11).
- Покупки не обходят SDK: нет внешних ссылок, своих платёжных форм и «подарочных кодов» в MVP.

## 5. Рекламы нет

- Ни rewarded, ни interstitial, ни баннеров. Модуль ads не подключается (00_MASTER §14).
- Значит, «продолжить за рекламу» нет. Continue на Defeat идёт только за Spare Hull (из инвентаря или через Hull Pack / Starter Crate).
- Для игрока это плюс: принудительные межстраничные объявления — одна из главных причин негатива ([AppFollow](https://appfollow.io/blog/what-mobile-game-players-want-monetization-insights-from-app-store-reviews)).

## 6. Онлайн-игра платформы

- Iron Burrow — **онлайн-игра**: профиль, прогресс (level-set, verified level end, награды), инвентарь, ежедневные награды, покупки и лидерборды живут на платформе и идут через SDK.
- Сама симуляция стадии клиентская (Canvas 2D, без realtime-сервера). Результат стадии отправляется через `progress` (verified level end), лидерборд обновляется по результату Siege.
- При потере связи (оценка, детали в разделе 31): текущую стадию даём доиграть. Отправку результата повторяем при восстановлении. Расход бустера подтверждаем через `inventory`. Если сеть пропала, покупки и награды недоступны и это явно видно игроку. Режима «играть без сети» как фичи нет.
