# Записи сервисов (configs)

Файлы `configs/remote/<scope>/<key>.json` — копии записей приложения на платформе; коммит файла
сам ничего не публикует. Формат файлов — [configs/remote/README.md](../../../configs/remote/README.md).
Клиент читает записи при запуске (снимок SDK) и дальше только точечно: нужный scope или запись,
один раз за сессию — `sdk.configs.get(scope, key)` из снимка, диапазоны уровней — модулем
`levels`. Повторных и широких перечитываний нет ([network.md](network.md)).

## Как записи попадают на платформу
Методами MCP платформы (поля вызовов — в описании методов MCP); до них — `npm run records`
([проверка до записи](#проверка-до-записи)):
1. **Сначала схема раздела** — `configs.schemas.put` для `scope`, если схемы ещё нет или она
   меняется (свои разделы игры — тоже).
2. **Затем пакетная запись** — `configs.write` всех записей раздела одним вызовом с текущим
   `schemaVersion` раздела.
3. **Чтение обратно** — `configs.get`: опубликованная `data` совпадает с файлом.

## Проверка до записи
Перед записью в сервисы — `npm run records` (`scripts/validate-records.mjs`, без сети). Он печатает
для каждого раздела, чем тот проверен, и ошибки строками `файл: путь в JSON: что не так`:
- **схема сервера** — `schemas/<scope>.json`: JSON Schema, по которой сервер принимает запись
  раздела (сам файл — схема, либо она в его поле `schema` рядом с версией). Схемы приложения
  сохраняют в `schemas/` в начале работы ([schemas/README.md](../../../schemas/README.md)); имя
  файла — имя раздела (`ui.hud.json`, `levels.main.json`), для разделов по шаблону годится и
  `levels.*.json` (сначала ищется точное имя). По схеме проверяется `data` записи (файл без
  конверта — целиком). Схемы у сервера есть для `ui.hud`, `ui.windows`, `ui.skins`,
  `localization`, `game.placements`, `levels.*`, `segments`, `filters.params`, иногда `ads.*` и
  `iap.*`;
- **SDK** — только когда файла схемы нет: то, чем запись читает клиент (`vendor/`):
  `localization/locales`, `ui.hud/layout`, `iap.offers/*`, `iap.settings.products/*`,
  `levels.<set>/set`;
- **`not validated: no schema`** — нет ни того, ни другого: раздел не проверен, а не «прошёл»;
- правило `progress/progress_main` без `data.profileProjection` (сервер отвергает запись с
  `PROGRESS_CONFIG_SCHEMA`) и связи между записями: `name`/`scope`/`key` = путь файла; оффер →
  продукт; плейсмент → оффер; `entities[].id` и `reward[].id` → предмет каталога; набор уровней →
  диапазоны; ключи текстов записей (`titleKey`, `descriptionKey`, `l10n`, `title`) → запись строк.

Для `progress`, инвентаря (`inventory.catalog`, `inventory.starter`, `inventory.exchange`),
ежедневных наград, лидербордов, продуктов и офферов схем сервера нет: их проверяет сам сервис при
пробной записи (dry-run). Для этих разделов прошедший `npm run records` — не достаточная
проверка: сначала пробная запись, потом настоящая.

## Диапазон уровней: `server.contentHash`
Запись диапазона `levels.main/r_*` несёт `data.server.contentHash` — sha256 (hex) от формы
RFC 8785 (JCS) объекта `data` без поля `server`. Запись диапазона без него не годится;
клиент передаёт `contentHash` уровня в `beginAttempt` и `levelEnd`. После любой правки `data`
хеш пересчитывает скрипт:
```sh
node scripts/levels-hash.mjs           # пишет хеш во все файлы configs/remote/levels.*/r_*.json
node scripts/levels-hash.mjs --check   # только сверяет; расхождение — код выхода 1
```

## Что закрыто для ключа приложения
Разделы инвентаря `inventory.exchange` (правила обмена) и `inventory.starter` (стартовый
баланс) пишет только владелец приложения: ключ приложения получает `FORBIDDEN`. Пока владелец их
не опубликовал, монеты в игре только копятся: стартового баланса нет, потратить их не на что
([inventory-and-currency.md](inventory-and-currency.md)).

## Удаление файлов
Удаление файла проекта доходит до платформы только после слияния изменений: сборка на
платформе до этого видит прежние файлы. Поэтому сборку на платформе запускают после слияния
изменений с удалениями, а не вместе с ними. Удаление файла в `configs/remote/` запись на
платформе не удаляет.

## Что требует платформа от записей нового приложения
Проверено публикацией этих образцов на чистом приложении:
- Предмет каталога инвентаря создаётся без поля `enabled` (сервис выставляет его сам).
- Запись прогресса не содержит `data.clientBudget`.
- Определение лидерборда требует `scopes`, `rateLimit`, `velocity`, `dedup`, `integrity`, `action` и не принимает `name`.
- Размещение магазина сначала заводится в реестре размещений `ads.game.placements` с тем же ключом
  (`configs/remote/ads.game.placements/placement_shop.json`), затем — в `iap.placements`.
- Порядок из-за ссылок: предмет инвентаря → продукты → офферы → размещения.
- Локализация пишется по локалям (ключ локали), пакетная форма записи для неё не подходит.
- Форму записи определяет платформа: если сервис отклонил запись, запись приводится к требуемой форме с теми же значениями.
